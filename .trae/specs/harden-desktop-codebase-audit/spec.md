# PlanMosaic Desktop 全局安全审查与优化 Spec

## Why
当前桌面端仍存在本地 HTTP API 无鉴权、渲染层 HTML 注入、提案审批信任客户端输入、并发写入不一致、配置边界过宽等问题。需要以一次完整的安全与稳健性加固为目标，统一补齐访问控制、输入校验、数据一致性和资源管理能力。

## What Changes
- 为桌面端本地 HTTP API 与控制通道补齐鉴权、Origin 限制、请求体大小限制和监听地址约束
- 修复渲染层 `innerHTML` 注入点，收紧 CSP，并统一采用安全的文本渲染策略
- 收紧敏感配置更新边界，禁止未授权修改上游地址、TLS 校验等高风险项
- 将提案审批改为服务端可信对象流转，禁止客户端伪造审批载荷直接改写数据
- 统一日程与历史写入路径，补齐锁、版本校验与 schema 校验，避免并发覆盖和脏数据落盘
- 修复 preload/前端事件解绑、全局保存锁、定时器与监听器清理等稳健性问题
- 为关键漏洞与回归路径补充自动化验证和审计清单

## Impact
- Affected specs: 桌面端本地服务安全、渲染层安全、提案审批一致性、数据持久化可靠性、CLI/UI 控制边界
- Affected code: `PlanMosaic Desktop/main.js`、`preload.js`、`index.html`、`ai-agent.js`、`server.js`、`paths.js`、`cli/bridge.js`、`cli/ui.js`、`backend/server.py`、`backend/tool_executor.py`、`backend/helpers.py`、`backend/config.py`

## ADDED Requirements
### Requirement: 本地 API 与控制通道必须具备最小暴露面
系统 SHALL 对桌面端本地 HTTP API 和 `/ui/*` 控制通道启用访问控制，禁止未认证或跨来源的任意调用修改本地数据。

#### Scenario: 未认证请求被拒绝
- **WHEN** 外部页面或本地进程未携带有效鉴权信息访问写接口或控制接口
- **THEN** 系统返回拒绝结果，且不修改任何本地数据

#### Scenario: 非白名单来源被拒绝
- **WHEN** 请求来源不在受信任 Origin 白名单内
- **THEN** 系统不返回宽松 CORS 头，且拒绝跨来源读写

#### Scenario: 超大请求体被拦截
- **WHEN** 客户端提交超过约定大小上限的请求体
- **THEN** 系统返回明确错误，并在读取完整请求前终止处理

### Requirement: 渲染层必须避免未转义 HTML 注入
系统 SHALL 禁止将用户输入、AI 提案内容或外部数据直接拼接到 `innerHTML` 中作为可信 HTML 渲染。

#### Scenario: 文本字段按纯文本呈现
- **WHEN** 大任务备注、提案原因、任务名称或对比内容包含 HTML 片段
- **THEN** 页面仅按文本显示，不执行脚本、不创建意外 DOM 节点

#### Scenario: CSP 拒绝内联执行
- **WHEN** 页面存在未经授权的内联脚本或事件处理器
- **THEN** CSP 阻止其执行，并要求改用受控脚本绑定方式

### Requirement: 提案审批必须基于服务端可信状态
系统 SHALL 仅允许审批服务端创建并持久化的提案对象，禁止客户端直接提交伪造提案载荷触发数据修改。

#### Scenario: 客户端伪造提案被拒绝
- **WHEN** 客户端直接提交未登记或已过期的 proposal 内容
- **THEN** 审批接口拒绝请求，且不执行任何数据修改

#### Scenario: 未知提案类型被拒绝
- **WHEN** 提案类型不在服务端明确定义的审批枚举中
- **THEN** 系统返回校验失败，而不是按通用逻辑写入脏数据

### Requirement: 配置更新必须分级并校验
系统 SHALL 将普通展示配置与敏感运行配置分级管理，禁止前端未经授权修改高风险网络与安全参数。

#### Scenario: 敏感配置禁止前端直接修改
- **WHEN** 客户端尝试修改 `baseUrl`、监听地址、TLS 校验或类似高风险配置
- **THEN** 系统拒绝修改，或仅允许通过受控管理入口变更

#### Scenario: 外链打开需严格匹配
- **WHEN** 系统请求打开外部链接
- **THEN** 仅允许符合协议与主机白名单的 URL 被打开

### Requirement: 数据写入必须保持一致性
系统 SHALL 通过统一写入入口、锁与版本校验保证日程、历史和配置数据在并发场景下不发生覆盖写或脏写。

#### Scenario: 并发保存不丢数据
- **WHEN** 多个保存、审批或工具执行请求同时修改同一份数据
- **THEN** 系统串行化写入或基于版本拒绝冲突写入，不出现后写覆盖先写

#### Scenario: 非法结构不落盘
- **WHEN** 请求载荷缺失关键字段、字段类型错误或包含未知结构
- **THEN** 系统返回校验错误，并保持原始数据文件不变

### Requirement: 前端事件与资源必须可回收
系统 SHALL 为 preload 监听器、流式回调、保存锁、定时器与动画帧提供成对注册/释放机制，避免重复回调、静默丢保存和资源泄漏。

#### Scenario: 单次请求只清理自身监听器
- **WHEN** 一次 AI 请求结束或失败
- **THEN** 系统只移除该请求关联的监听器，而不影响其他进行中的流程

#### Scenario: 保存冲突可感知
- **WHEN** 用户在保存未完成时再次触发保存
- **THEN** 系统排队处理或明确提示冲突，而不是静默丢弃本次操作

## MODIFIED Requirements
### Requirement: 桌面端本地服务默认仅限本机受控访问
系统原有本地服务能力继续保留，但必须默认绑定到 `127.0.0.1`，并通过受控鉴权与来源限制暴露最小必要接口。

### Requirement: AI 与日程数据渲染以安全文本优先
系统原有消息、提案、任务和备注渲染能力继续保留，但所有动态内容必须先经过统一的文本转义或安全 DOM 构建流程后再呈现。

## REMOVED Requirements
### Requirement: 客户端可直接提交完整提案对象完成审批
**Reason**: 该模式会使审批链路信任客户端输入，允许伪造提案直接修改日程数据。
**Migration**: 改为客户端提交 `proposal_id` 或服务端签名标识，由服务端读取可信提案后执行审批。
