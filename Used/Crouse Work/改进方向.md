## 二、改进方案：做加法，不动刀

### 2.1 🎯 核心功能：ReAct 对话转录（一键生成）

**思路**：不改现有的 native function calling 交互模式，而是加一个 **"导出 ReAct 记录"** 按钮。用户完成一次对话后，系统把隐式的 tool calls 回放成显式的 ReAct 文本。

**为什么这样做是对的**：
- Native function calling 本质上就是 ReAct——API 内部经历了"理解意图→选择合适的 tool→构造参数"的推理过程，只是格式不同
- 生成 ReAct 文本 = 把 OpenAI function calling 格式**翻译**成 ReAct 格式，这要求你对两种范式都有深刻理解
- 课程目的是"理解 ReAct"，不是"强迫用户用更差的交互方式"
- 现有思路链（`【思考】【/思考】`）可以直接作为 Thought 的素材

**转换逻辑**：

```
原始 function calling 流程：
  user: "帮我查爱因斯坦活了多久"
  assistant: {tool_calls: [{function: {name: "wikipedia_search", arguments: {query: "爱因斯坦 出生 去世"}}}]}
  tool: {result: "爱因斯坦1879年3月14日出生，1955年4月18日去世"}
  assistant: {tool_calls: [{function: {name: "calculator", arguments: {expression: "1955 - 1879"}}}]}
  tool: {result: "76"}
  assistant: {content: "爱因斯坦活了76岁。"}

↓ 转录为 ReAct 格式 ↓

  Question: 帮我查爱因斯坦活了多久
  
  Thought: 用户想知道爱因斯坦的寿命，我需要先查他的生卒年份。
  Action: wikipedia_search(query="爱因斯坦 出生 去世")
  Observation: 爱因斯坦1879年3月14日出生，1955年4月18日去世
  
  Thought: 已知出生1879年，去世1955年，计算差值即可得到寿命。
  Action: calculator(expression="1955 - 1879")
  Observation: 76
  
  Thought: 计算完成，可以直接回答用户了。
  Final Answer: 爱因斯坦活了76岁。
```

**实现方式**：
- 对话历史中已保存完整的 messages（含 tool_calls 和 tool results）
- 遍历 messages，提取 user → assistant(tool_calls) → tool(result) → assistant(content) 的序列
- 对每一步生成对应的 Thought（可调一次轻量 LLM 润色，也可以用规则模板）
- 最终输出为纯文本/PDF/图片，方便交作业

**三端实现**：
- 桌面端：在对话底部加一个 `📋 生成ReAct记录` 按钮，点击弹窗展示并支持复制
- Android 端：在 MosaScreen 右上角菜单加选项
- Uni-app 端：同样加按钮

### 2.2 🔧 新增实用工具

现有工具围绕"日程 CRUD + 深度分析"，下面新增的工具让 Agent 的能力从"操作日程"扩展到"辅助决策"。

#### 工具 1：任务时间估算器（可训练小模型）

**功能**：给定任务描述，估算合理完成时间。

**为什么有用**：用户添加任务时经常不知道预计多长时间，导致排期不合理。这个工具帮助用户建立对任务耗时的合理预期。

**实现层次**（从简到深）：

| 方案 | 复杂度 | 说明 |
|------|--------|------|
| A. LLM Prompt | 低 | System Prompt 中加入 "你是一个任务时间估算专家..."，让 Agent 自己估算 |
| B. 历史数据统计 | 中 | 收集用户历史任务的"预计 vs 实际"耗时，计算相似任务的典型耗时 |
| C. 训练小模型 | 高 | 用历史数据训练一个轻量回归模型（如 scikit-learn RandomForest），输入任务名+类别，输出预估分钟数 |

方案 B 和 C 可以用 Python 实现（一个小 Flask 服务提供 `/api/estimate-time` 端点），三端前端通过 HTTP 调用。

**工具 Schema 示例**：
```json
{
  "name": "estimate_task_time",
  "description": "根据任务描述估算合理完成时间",
  "parameters": {
    "task_name": "string",
    "category": "学习|工作|生活|运动",
    "context": "string (可选，如'有一定基础')"
  }
}
```

#### 工具 2：网络搜索评估

**功能**：用户描述一个目标或问题，Agent 搜索网络资源，汇总可行的解决方案和评价。

**为什么有用**：
- "我想学机器学习，有什么推荐的学习路径？" → 搜索多个平台的经验贴，汇总对比
- "这个任务怎么做更高效？" → 搜索方法论，给出优化建议
- 填补 LLM 知识截止日期之后的信息空白

**实现方案**：
- 调用 Bing Web Search API / SerpAPI / DuckDuckGo Instant Answer API
- 返回前 3~5 条结果的标题 + 摘要
- Agent 对搜索结果做二次加工，而不是原样扔给用户

**工具 Schema 示例**：
```json
{
  "name": "web_search_evaluate",
  "description": "搜索网络资源，评估和汇总任务解决方案",
  "parameters": {
    "query": "string (搜索关键词)",
    "purpose": "string (搜索目的，如'学习路径'、'最佳实践'、'时间评估')",
    "max_results": "number (默认5)"
  }
}
```

#### 工具 3：日程健康度检查

**功能**：从多个维度评估用户当前日程的健康状况。

**已有基础**：Android 端 [analyze](file:///d:/Trae CN/Projects/PlanMosaic/PlanMosaic AndroidStudio/app/src/main/java/com/example/planmosaic_android/util/agent/ToolExecutors.kt) 工具已有 `patterns`、`optimize`、`ddl_status`、`habits` 四个分析维度——直接复用并增强。

可以增加的维度：
- **负荷均衡度**：是否某几天过载、某几天空闲
- **休息保障**：是否连续多天没有休息时间块
- **时间分配**：学习/工作/生活/运动的时间占比是否合理
- **DDL 压力指数**：近期 DDL 密集度

在 `analyze` 工具的 action 枚举中加 `health_check` 即可。

### 2.3 🐍 Python 的定位（可选层）

Python 不是必须的，但如果要做**任务时间估算模型训练**、**更复杂的数据分析**，Python 生态确实更方便。建议的引入方式：

```
现有架构：
  Electron/Android/Uni-app → server.js → DeepSeek/Qwen API

加 Python 后（完全可选）：
  Electron/Android/Uni-app → server.js → Python 微服务 (estimator / analyzer)
                                       ↘ DeepSeek/Qwen API
```

Python 仅作为一个**旁路计算服务**，提供：
- `/api/estimate-task-time` — 时间估算
- `/api/analyze-workload` — 工作负载分析
- `/api/train-model` — 模型训练接口（低频调用）

**不替代任何现有模块**。server.js 的主流程不变，只是在需要时调用 Python 服务。

### 2.4 📊 多步调用演示案例

不需要改架构，只需准备几个能展示多步 tool calling 的 **演示对话**：

**案例 1：查资料 + 排日程**
```
用户："帮我查一下番茄工作法的最佳实践，然后在我明天下午安排两个番茄钟时段"

Agent 调用链：
  1. web_search_evaluate("番茄工作法 最佳实践") → 返回搜索结果
  2. view_schedule("明天") → 查看明天是否空闲
  3. add_schedule(明天 14:00-14:25, 14:30-14:55) → 安排两个25分钟时段
```

**案例 2：时间估算 + 任务拆解**
```
用户："我下周一要交一个2000字的实验报告，帮我规划一下"

Agent 调用链：
  1. estimate_task_time("写2000字实验报告", "学习") → 估算约6小时
  2. view_schedule("本周") → 查看空闲时间
  3. manage_big_tasks(break_down) → 拆解为子任务分配到各天
```

**案例 3：搜索 + SWOT + 决策**
```
用户："我在纠结考研还是直接工作，帮我分析一下"

Agent 调用链（深度规划模式）：
  1. web_search_evaluate("计算机专业 考研vs就业 2025") → 了解当前形势
  2. swot_analysis("考研", user_context=...) → 结构化分析
  3. swot_analysis("直接工作", user_context=...) → 对照分析
  4. decision_matrix(...) → 多维度打分
```

### 2.5 📝 开题文档特殊优势

相比从头开始做选题一的同学，本项目有独一无二的开题素材：

**技术调研可以写成对比研究**：
> "我们团队在 PlanMosaic 项目中已经实践了 OpenAI Function Calling 范式，本次选题将深入研究其底层原理——ReAct 范式，并对两种方案进行对比分析……"

**核心原理可以结合实际代码讲**：
> "在现有的 AgentRepository.kt 中，callWithTools 方法实现了递归的工具调用循环（见代码第 125-190 行）。转换为 ReAct 范式后，我们将手写这一循环，深入理解每一步的状态管理……"

**分工可以按"研究 + 增强"来**：
- 同学 A：ReAct 转录功能（理解并实现两种范式的转换）
- 同学 B：新工具开发（时间估算、网络搜索）+ Python 微服务
- 同学 C：演示案例 + 开题文档 + 视频
